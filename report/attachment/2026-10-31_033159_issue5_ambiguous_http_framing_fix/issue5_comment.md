## この課題の噛み砕いた解説

### 前提: HTTP リクエストの「終わり」はヘッダで決まる

HTTP/1.1 では、1 本の TCP 接続にリクエストが次々と流れてきます。受け取る側は、どこまでが 1 つ目のリクエストの body なのかをヘッダから判断します。方法は 2 つあります。

- **`Content-Length: 100`**: body は 100 バイト
- **`Transfer-Encoding: chunked`**: body は「長さ + データ」の塊（チャンク）の並びで、長さ 0 のチャンクで終わる

RFC 9112 は、この 2 つが矛盾する要求（値の違う `Content-Length` が複数ある、`Transfer-Encoding` と `Content-Length` が両方ある、など）を、エラーにするか接続を閉じて扱うように求めています。どちらの解釈が正しいか決められないからです。

### 何がまずいのか: 区切りの解釈が 2 台でずれる

mesh-llm の前に nginx などのリバースプロキシを置く構成を考えます。

```
クライアント ──▶ 前段プロキシ ──(1 本の接続を使い回す)──▶ mesh-llm (9337)
```

前段プロキシと mesh-llm が同じリクエストの終わりを違う位置だと解釈すると、片方にとっての「body の続き」が、もう片方には「次のリクエスト」に見えます。これが **HTTP request smuggling**（リクエストの密輸）と呼ばれる攻撃の仕組みです。

具体例（Content-Length の重複）:

```
POST /v1/chat/completions HTTP/1.1
Content-Length: 10
Content-Length: 500
...
```

- 前段プロキシが **最初の値**（10 バイト）を使い、mesh-llm が **最後の値**（500 バイト）を使うと、
- mesh-llm は、プロキシが同じ接続で続けて送った **別のユーザーのリクエスト** まで、攻撃者のリクエストの body として読み込んでしまいます
- その結果、他人のリクエストの中身（プロンプト、`Authorization` ヘッダなど）が攻撃者のリクエストに混ざる、あるいは他人のリクエストが壊れる、といったことが起こりえます

`Transfer-Encoding` と `Content-Length` が両方ある場合も同じで、片方が CL、もう片方が TE を信じると区切りがずれます。`Transfer-Encoding: chunked, identity` のように `chunked` が最後にない値や、表記を少し崩した値も、実装ごとに解釈が分かれやすいところです。

### mesh-llm の現状のふるまい

| 入力 | 安全な扱い | mesh-llm の現状 |
|---|---|---|
| 値の違う `Content-Length` が複数 | 400 で拒否 | **後の値で上書きして受理** |
| `Transfer-Encoding` と `Content-Length` が両方 | 400 で拒否（または接続を閉じる） | **CL を黙って捨てて受理**（TE を優先） |
| `Transfer-Encoding` の最後が `chunked` でない | 400 で拒否 | **`chunked` がどこかに含まれていれば chunked として受理** |

さらに、mesh-llm は受け取ったリクエストを後ろ（llama-server や別ノード）に転送するとき、body を書き換えない場合は **元のあいまいな framing ヘッダをそのまま付けて** 送ります。mesh-llm と転送先の解釈がずれる可能性も残ります。

### どのくらい危ないか

- 攻撃が成立するには、mesh-llm の前に **接続を使い回すプロキシがあり、そのプロキシがこうした要求を通して、mesh-llm と違う解釈をする** 必要があります。mesh-llm を直接公開しているだけなら、影響はほとんどありません
- mesh-llm は転送先に `Connection: close` を付けて 1 接続 1 リクエストにしているので、転送先との間でずれが起きても、影響はそのリクエストの中にとどまりやすい作りです
- 一方で、前段プロキシ側で他人のリクエストが混ざる経路は、mesh-llm 側だけでは防げません。そのため、受け取る段階で拒否するのが定石です
- この判定はコードを読んだ結果で、実際に再現して確かめたものではありません

### 直し方の方針

1. 値の違う `Content-Length` の重複、TE と CL の併存、最後が `chunked` でない TE は、**400 で拒否** する
2. 後ろに転送するときは、元の `Content-Length` / `Transfer-Encoding` を捨てて、**mesh-llm が実際に読んだ body の長さから作り直す**

jimoto-no-llm/mesh-llm の PR #21 がこの方針で修正しているので、移植の候補になります。
